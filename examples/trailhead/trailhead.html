Trailhead: an uncoupled design

Trailhead is an offline phone app for day hikers. It shows a downloaded trail map without coverage, records the walked route, sends an SOS text with the hiker's position, and shows the trailhead forecast. It has no backend. Every design matrix in the model is diagonal: each design parameter changes exactly one functional requirement.

Boundary and constraints

Inside: the offline map, the track recorder, the SOS sender, and the forecast view, all on the hiker's device. Outside: the tile publisher, the weather service, the SMS carrier, the GPS hardware, and the operating system. The app is responsible up to the SMS handoff to the operating system; carrier delivery is not claimed.

  • offline_first: map, recorder, and SOS work without mobile data.
  • on_device_only: all state stays on the device.
  • sampling_range: the sampling interval is 1 s to 10 s.

Workload day_hike: one hiker, trips up to 12 h, region packs up to 500 MB. All numeric criteria are proposed targets, not user-supplied.

Each row shows a proposed pairing from a need through an FR and DP to a PV. An FR is a functional requirement. A DP is a design parameter. A PV is a process variable that realizes a DP. These lines show traceability, not proof that other influences are absent. The brackets identify the two decomposed parents.

Decomposition by zigzagging

The functional tree was not drawn first. The child FRs of FR2 and FR3 exist only because DP2 and DP3 were chosen: a recorder pipeline needs sampling and persistence, and a beacon with its own fix request needs a position result and a dispatch. FR1 and FR4 stop at level 1 because one module with owned state, a contract, and an acceptance check already covers them.

The master matrix matters most. Local diagonals do not prove whole-system independence; the cross-branch cells, such as DP2.1 against FR3.1 (both use the location service) and DP1 against FR2.2 (both write to storage), had to be argued one by one.

Why the zeros hold

Every module touches some resource that another module also touches. Each such contact is a candidate off-diagonal term. The design removes each one with a mechanism in the owning DP, not with a module boundary.

The architecture style

The proposed style uses modules with owned state and parent-owned contracts. A contract defines the records and interfaces that modules exchange. The app can ship as one binary. Separate deployment is not a condition for independence.

  1. Each leaf DP owns its stated state. Map pack, sampling configuration, track log, emergency contact, and forecast snapshot each have one logical writer.
  2. Children receive data through their parent's contracts. This boundary exposes ownership, but it does not remove effects through data or shared resources.
  3. The parent defines shared records before its children use them. Each child depends on that contract. A contract change can still affect several child FRs.
  4. Each criterion retains its stated measurement point. The dispatcher's 2 s interval starts at a ready result. This definition alone does not prove independence.
  5. Preallocation, the battery floor, and the SOS timeout address shared-resource risks. Their effectiveness still needs evidence under the stated workload and failure conditions.
  6. The shell composes outputs. Composition preserves independence only when its behavior does not introduce material effects between the FRs.

Runtime order differs from design order. The model classifies DP2 and DP3 as diagonal from their authored influence claims, so their design junctions are S. Their runtime flows still specify sequences. A C junction states a required design order, not an automatic runtime order.

M1
map_pack_renderer
realizes DP1
  • A region that the hiker selects for download.
  • A viewport (center and zoom) from the app shell.
  • A rendered map layer for the viewport.
map_pack
  • Rendering never makes a network request.
  • Only a pack whose checksum matches is used for rendering.
When the pack is missing or its checksum fails, show that the region has no offline map and offer a download. Never fetch tiles while rendering.
M2.1
sampling_policy
realizes DP2.1
  • Location updates from the operating system.
  • The battery level from the operating system.
  • The interval that the hiker selects.
  • Accepted fixes in the recorder's Fix record format.
sampling_settings
  • The interval stays from 1 s to 10 s.
  • No two consecutive accepted fixes are more than 15 s apart while recording.
  • Sampling stops below 15 % battery.
When the location service reports no fix, keep the subscription and report a no-signal state. Below 15 % battery, stop sampling and report a paused recording.
M2.2
fix_log
realizes DP2.2
  • Fixes in the recorder's Fix record format, passed by the recorder pipeline.
  • One acknowledgement per durable fix.
  • The stored track for review and export.
track_log
  • A fix is acknowledged only after it is flushed.
  • The log is append-only during a recording.
When preallocation fails, refuse to start the recording and tell the hiker how much space is needed. When a write fails, stop acknowledging and report the recording as interrupted.
M3.1
fix_acquirer
realizes DP3.1
  • An SOS confirmation.
  • Fixes and the last known fix from the operating system.
  • One PositionResult: a fix with accuracy and age, or an explicit no-fix result.
nothing
  • Exactly one PositionResult per confirmation.
  • A result with a fix always states accuracy and age.
When no fix arrives within 7 s and no last known fix exists, return the no-fix result so that the SOS is still sent.
M3.2
sms_dispatcher
realizes DP3.2
  • One PositionResult, passed by the beacon sequence.
  • One SMS handoff to the operating system for the stored contact.
emergency_contact
  • Exactly one handoff per confirmation.
  • The message always names the hiker and states either the position or that the position is unknown.
When no contact is stored, block the SOS button during setup instead of at the moment of need. When the operating system rejects the handoff, show the message text so that the hiker can send it by hand.
M4
forecast_cache
realizes DP4
  • The trailhead coordinates.
  • Forecast responses from the weather service when online.
  • The device clock.
  • The stored forecast with its issue time and a stale label when it is older than 24 hours.
forecast_snapshot
  • A displayed forecast always shows its issue time.
  • A forecast older than 24 hours always carries the stale label.
When a fetch fails, keep the previous snapshot and its issue time. Never show a forecast without its issue time.

Composite modules: M0 trailhead_app contains M1, M2, M3, M4. M2 contains M2.1 and M2.2. M3 contains M3.1 and M3.2. Composites own no state. Every leaf module declares dependencies = [].

Source layout

The proposed numbered layout connects model identities to source paths. A dp folder identifies a selectable mechanism, and a tests/fr folder identifies its paired requirement. The adhcl-scaffold checker reports folder-name tokens in text. Such a token identifies a potential dependency, not a proven off-diagonal influence. No token does not establish zero influence. The model's influence claims still need causal review and behavioral evidence.

The numbered layout is optional. Parent mediation does not remove influences through data, state, or shared resources. The scanner reports test tokens without executing tests. Its --expect flags enforce explicit structural policies, not axiomatic design classifications.

What adhcl established

  • adhcl validate examples/trailhead/trailhead.ad.hcl exits 0 under the source profile. All four scopes are uncoupled.
  • Under --profile architecture it reports two unresolved_refinement errors, for DP2 → FR2 and DP3 → FR3. Core version 1 treats any material effect above leaf level as an obligation that needs a reviewed outcome argument, and it has no input for such a review. Removing the two parent diagonals would make the root scope unresolved instead, so the model keeps the true claims.
  • Every claim carries a support_gap warning: a structural classification is not proof that the stated effects are true.

Open before this design is trusted

  • location_service_shared (to validate): one client's fix request does not pause another client's updates. Four zeros depend on it. Test on each target OS with the recorder at 1 s and repeated SOS requests.
  • preallocation_honored (to validate): reserved file space cannot be taken by other writes. Two zeros depend on it. Run large_download_while_recording.
  • Allocation of FR3: 8 s for the fix plus 2 s for dispatch should give the 10 s handoff target. This is an argument to review, not a modelled fact.
  • Information content: no alternative was compared on measured joint success, so information content is unknown. A run of the leaf scenarios on target devices would give the joint success rate that the Information Axiom needs.
